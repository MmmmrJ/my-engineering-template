# 使用 Codex Product Design 生成原型并保持实现一致的方法

## 目的与适用范围

本 SOP 用于所有新增或改变页面、用户流程、交互、响应式布局或视觉设计的需求。目标是在 Codex 与 Cursor 间建立“原型、资产、规格、实现、视觉验收”的可追溯闭环，使高保真实现以已确认、已冻结的设计为唯一基线。

纯后端需求必须在 Feature Spec 中标记 `设计交付：not-applicable`，不适用本 SOP。探索阶段未被选中的方案、外部链接和聊天中的截图均不是实现或验收依据。

## 核心规则

- 原型截图本身不是实施契约。`design.md`、`prototypes/` 下的本地原型图和 `assets/manifest.md` 共同构成实施契约。
- 用户指定的 skill 或插件只产生可追溯的候选输入，不能绕过设计冻结、用户确认、实施前校验或最终视觉验收。
- 未经确认的视觉、交互或资产差异默认是缺陷。实现角色不得以“优化”“相似”或技术习惯替换冻结设计。
- 设计确认后，前端先还原静态视觉，再接入业务逻辑；业务接入不得改变已冻结的信息层级、布局、资产或交互，除非形成新设计版本并重新审核。
- 所有用于实现与验收的图标、背景图、插画、纹理和照片必须本地可用、来源可追溯、授权可说明，并在资产清单中冻结。

## 目录与版本契约

每个功能在方案阶段创建以下目录，模板见 [设计交付物说明](README.md)：

```text
docs/design/<feature>/
├── design.md
├── prototypes/
├── assets/
│   └── manifest.md
├── verification.md
└── verification/
```

`design.md` 必须包含以下章节：`原型来源与能力记录`、`资产清单`、`设计冻结`、`关键视觉不变量`。它必须明确记录：

- 方案版本（例如 `方案 V2`）和资产版本（例如 `assets V2`）；两者均为可追溯版本号。
- 资产清单位置 `assets/manifest.md`，及资产冻结状态 `draft` 或 `frozen`。
- 每个验收场景的固定视口、状态、测试数据或夹具、权限和本地原型图。
- 关键尺寸、间距、字号、颜色、图标、背景图、裁切和交互限制；这些是实现与 QA 的视觉不变量。

冻结资产文件保存在功能目录的 `assets/` 下；`assets/manifest.md` 是每项资产的唯一清单：冻结文件、运行时路径/图标包、来源与许可、实现规范、替代规则必须与设计版本对应。替换文件、变更裁切焦点、图标集合/版本或视觉样式时，均须提升资产版本；如影响已确认视觉或交互，也须创建新方案版本并重新审核。

## 端到端 SOP

### 1. 能力请求登记

父 Agent 在委派前登记用户点名的 skill 或插件、适用角色、预期产物、输入来源、输出位置和降级方案。UI 角色将实际使用的能力、版本（如可得）、日期、提示摘要/来源和产物路径写入 `design.md` 的“原型来源与能力记录”。

可选增强不可用时，使用共享 skill 完成相同的规格工作，并记录降级事实；不得静默切换视觉方向、资产策略或未获授权的第三方来源。Codex 专属能力不得成为 Cursor 的硬依赖。

### 2. 原型探索与方向选择

探索可使用占位图、生成图或多种视觉方向，但每项候选必须标明候选状态、来源和限制。候选资产只能用于探索，不能进入冻结清单或最终验收。

UI 角色输出用户流程、信息层级、页面状态、响应式与无障碍要求，并把候选原型本地化保存到 `prototypes/`。用户选择一个方向后，未选方向不构成实施基线。

### 3. 资产入库与冻结

在设计规格化前，将选中资产的最终版本保存到本地，并建立 `assets/manifest.md`。每一项均须说明语义用途、使用场景、来源/作者或生成能力、许可或用户授权、冻结文件、运行时引用和完整实现规则。

资产清单和资产文件完成后，`design.md` 仍处于 `draft`，直至方案取得明确用户确认。确认后将设计与资产状态标为 `frozen`，并锁定方案版本、资产版本、原型图、测试数据和视觉不变量。父 Agent 必须保存“用户已确认：方案 Vn”的记录；子 Agent 不能自行宣布获批。

### 4. 设计规格化与用户确认

UI 角色在 `design.md` 中完整定义每个场景：固定视口、权限、测试数据、原型图、布局、令牌、组件变体和以下状态：默认、加载、空、错误、成功、禁用、权限不足、延迟与离线（不适用时需明确说明）。规格还必须规定语义、键盘顺序、焦点可见性、颜色对比度、200% 缩放、减少动效和屏幕阅读器名称。

将带版本号的方案交由用户审核。用户反馈导致范围、交互、资产、数据、视觉不变量或验收标准变化时，创建新方案版本；不得从沉默、历史确认或模糊回复推断同意。

### 5. 静态还原与业务接入

前端只能消费已确认且冻结的 `design.md`、本地原型图与资产清单。实施前运行：

```text
node scripts/harness/cli.mjs validate-design docs/design/<feature>
```

先以设计矩阵中固定的视口、状态、权限和测试数据完成静态还原。不得新增模块、重排信息层级、自行补齐未定义交互，或替换图标/图片。发现规格冲突、资产缺失或技术限制时，登记偏差并交回父 Agent 与 UI 角色判定；不得自行接受。

业务逻辑接入只在静态视觉被保留的前提下进行。新接口状态、权限或数据长度导致视觉变化时，补全设计状态与测试数据，并按影响程度重新审核。

### 6. 截图 QA 与偏差闭环

QA 仅以冻结版本验收。在与原型完全相同的视口、浏览器环境、状态、权限、数据/夹具和资产版本下采集实现截图，保存到 `verification/`。`verification.md` 要逐行映射每个原型场景与实现截图，记录比较方法、资产一致性检查和结论。

比较覆盖默认、加载、空、错误、成功、禁用、权限/离线状态，以及所有设计矩阵中的桌面、平板和窄屏场景。固定环境截图、冻结资产、关键视觉不变量和分级人工评审是基线；不采用跨浏览器脆弱的通用像素差阈值。

偏差分级与放行规则：

| 级别 | 定义 | 处理规则 |
|---|---|---|
| P0 | 阻断任务、核心层级、关键操作、可访问性或品牌/合规资产错误 | 必须修复；不得 `pass`。 |
| P1 | 布局、信息层级、状态、关键尺寸、图标或背景图与冻结设计不一致 | 必须修复；不得 `pass`。 |
| P2 | 低影响细节差异，且不改变任务、层级、可读性或品牌语义 | 必须记录影响，标为 `accepted`，由具名 UI 确认人确认后才能 `pass`。 |

运行以下命令后，才可将 UI 验收标记为通过：

```text
node scripts/harness/cli.mjs validate-visual docs/design/<feature>
```

任何 P0/P1、未关闭偏差、未具名确认的 P2、设计版本不匹配或资产版本不一致都必须使验收结论为 `blocked` 或 `fail`，直到闭环完成。

## 图标规则

- 优先使用已批准、版本锁定的图标库，或仓库中的本地 SVG。清单必须固定包名与版本、图标名、`viewBox`/尺寸、描边或填充、颜色、默认/悬停/禁用状态和无障碍名称。
- 禁止以 emoji、Unicode 字符、临时手绘 CSS 或“相似图标”替代已冻结图标。图标不可用时登记为偏差，取得 UI 确认后才能使用替代项。
- 装饰性图标使用空替代文本或 `aria-hidden`；承载操作或状态含义的图标必须具有可访问名称，且不能仅靠颜色表达状态。
- 运行时图标包必须锁定版本；不得通过未版本锁定的 CDN 或外部链接临时加载。

## 背景图、插画与纹理规则

- 背景图、插画、纹理和照片必须使用本地、可追溯资产。外链图片不能作为运行时视觉依赖；第三方或品牌资产必须记录来源及许可/用户授权。
- 每项背景资产记录原始尺寸、格式、压缩版本、显示区域、`cover`/`contain` 规则、裁切焦点、遮罩或叠层、文字对比度，以及桌面/移动端变体。
- 由用户指定 skill/插件生成的资产，记录生成能力、日期、提示摘要和最终冻结文件；不要把生成服务链接作为唯一来源。
- 设计冻结和最终验收必须使用真实冻结资产。探索期占位图必须显式标注；若最终需替代资产，只能作为经 UI 确认的 P2（或更高）偏差处理。

## Subagent 约束

| 角色 | 可以做 | 不可以做 |
|---|---|---|
| 父 Agent | 登记能力契约、保存用户确认、委派、协调变更与最终交付 | 将用户确认或偏差接受权下放给 subagent。 |
| UI 设计 | 原型入库、资产清单、设计规格、冻结建议、视觉不变量与偏差判定 | 自行宣布设计获批、修改业务代码、接受自己的偏差。 |
| 前端 | 消费冻结设计/资产、保存实现证据、报告实现限制 | 新增模块、替换/重绘资产、重排层级、自行批准偏差。 |
| QA | 以冻结版本采集截图、比较、记录偏差与风险 | 以候选原型验收、关闭 P0/P1、无 UI 确认接受 P2。 |

所有 subagent 均不得创建下级 agent、修改团队状态或改变已确认范围。若用户指定的能力不可用，只可采用登记过的降级方案；不能以插件差异为理由降低冻结、资产或验收要求。

## 推荐委派提示词

```text
用户已指定能力：<skill / 插件>；适用角色：<角色>；预期产物：<路径>；
能力限制与降级方案：<说明>。请仅使用已确认的方案 <方案 Vn>、资产版本 <assets Vn>
及 docs/design/<feature>/ 下的冻结原型和 assets/manifest.md。不得重新设计、替换资产或接受偏差。
发现缺口时登记偏差并交回父 Agent。验收截图必须匹配设计矩阵中的视口、状态、权限、数据与资产版本。
```

## 交付检查清单

- [ ] `design.md`、本地 `prototypes/` 和 `assets/manifest.md` 均已创建并互相引用。
- [ ] 每个场景已定义固定视口、状态、测试数据/权限和关键视觉不变量。
- [ ] 图标与背景资产均可本地获得，来源/许可、版本和实现规则完整。
- [ ] 用户已明确确认当前方案版本，设计与资产均冻结。
- [ ] 实施前 `validate-design` 通过；验收前每个原型场景均有同条件的实现截图。
- [ ] `verification.md` 的资产一致性为 `pass`，所有偏差已按 P0/P1/P2 处理，`validate-visual` 通过。
